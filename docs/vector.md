# 检索与向量化选型说明（P1-8）

> 结论先行：**检索默认走 SQLite FTS5 + BM25**（零依赖、离线、可审计）；
> 语义向量检索（sqlite-vec / Chroma）是**可选增强**，按数据规模与场景按需启用。
> 本项目红线：只处理明文输入，不碰任何内存取 key / 数据库解密。

## 1. 为什么默认 FTS5 + BM25

| 维度 | FTS5 + BM25（现默认） | sqlite-vec 向量检索 | Chroma（第三方库） |
|---|---|---|---|
| 依赖 | 内置 SQLite，零安装 | 需编译加载扩展 | 需 pip 安装，自带后端 |
| 数据安全 | 纯本地文件，无网络 | 纯本地文件 | 本地但额外进程/目录 |
| 中文检索 | 子串/分词可控，BM25 排序可解释 | 需要 embedding 模型与向量化管线 | 同上 |
| 可审计性 | SQL 可见、结果可复现 | 向量近似，较难逐条解释 | 同向量方案 |
| 商业分发 | 无授权风险 | MIT/类 BSD，需随包分发扩展 | Apache 2.0，体积大 |

电商客服群检索的核心诉求是**命中可解释、可回原文**——BM25 词频排序天然满足；
群消息量大头是短文本，FTS5 在万级消息上毫秒级返回。

## 2. 本项目已落地的 FTS5 增强

- `db.py::rebuild_fts`：rebuild 后立即 `optimize`（压缩 FTS 索引，长期运行不膨胀）。
- `search.py`：FTS 分支改为 `ORDER BY bm25(messages_fts), time DESC`——相关度优先，同分按时间倒序。
- FTS 异常自动降级 LIKE 子串匹配（中文兜底，保证检索永不失败）。

## 3. sqlite-vec 什么时候启用

| 场景 | 建议 |
|---|---|
| 群消息 ≤ 5 万条、检索以关键词为主 | 不用向量，保持现状 |
| 需要"语义近义"召回（如"物流"→"快递/发货"） | 启用 sqlite-vec + 本地 embedding（如 bge-small-zh），入库时向量化 |
| 知识库问答（AI 客服训练集） | 向量召回 + BM25 混合（RRF 融合），见 `chat_archive/vector.py` 预留接口 |

启用方式（不随默认构建分发）：
1. 下载 sqlite-vec 预编译扩展（对应平台 arm64/x64）；
2. 在 `Database.connect` 中 `load_extension`；
3. 消息入库时写入 `message_vectors` 表；检索时 `vector_top_k` 与 FTS 结果 RRF 融合。

## 4. 权衡红线（避免过度工程）

- **不为向量而向量**：群消息运营分析（统计/信号/考核）与知识沉淀（FAQ）以结构化为主，向量只服务于"语义问答"这一个场景。
- **不引入重量级向量库进默认依赖**：保持 `pip install` 后零配置可跑（商业分发友好）。
- **数据不出本机**：任何 embedding 都应在本地跑小模型，禁止调用云 embedding 接口把群消息外发。
