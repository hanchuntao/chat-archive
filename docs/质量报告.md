## 一、交付形态与架构合理性（对照主流软件）

### 1.1 两层架构（用户确认的最终形态）

```
输入（微信/QQ 导出明文 TXT/MD/JSON/CSV，或加密备份）
   │
   ├─ 数据层：chat_archive/ 包（Python 标准库，零第三方依赖）
   │    ├─ pipeline/ingest.py   导入路由（按扩展名自动选解析器）
   │    ├─ importers/plain.py   TXT/MD/CSV 解析（正则与业务层同源）
   │    ├─ importers/wechat_json.py  JSON/JSONL（wechat-cli/WeFlow 兼容）
   │    ├─ pipeline/clean.py     噪声过滤（去重/占位符/灌水词）
   │    ├─ pipeline/desensitize.py PII 脱敏（掩码/泛化/整条剔除，8 规则）
   │    ├─ db.py                 SQLite+FTS5（幂等入库/群边界/全文索引）
   │    ├─ search.py / report.py / stats.py / vector.py / llm.py
   │    └─ cli.py                CLI 入口（init/import/search/stats/report/
   │                              weekly/vectorize/info/backup + --version）
   │
   └─ 业务层：skill/scripts/chat_archive.py（单脚本 ~2800 行，纯标准库）
        有效回复统计 → 员工日报 → 讨论要点/跟进 → 知识库沉淀（脱敏草稿）
        → AI 监督考核 → 丢单/商机信号 → 活跃度/响应速度 → 记忆层（增量锚点）
        → 需求洞察 → 质检信号 → 挂起队列 → SLA/满意度/健康分 → SOP 合规审计
        → 漏斗/问题分级 → 会话时间线/媒体归档 → @提及/消息明细 → HTML 看板
        → 快照保留（30 份）→ 周期环比 → 成长报告（17 个业务子命令）
```

### 1.2 与主流软件的对齐点

| 维度 | 本项目的做法 | 主流软件参照 | 对齐情况 |
|---|---|---|---|
| 存储 | SQLite + FTS5 全文检索，零运维 | 单机工具（如 Typora 系、本地优先工具） | ✓ 10 人电商规模最合适；用户已确认非 PostgreSQL |
| 导入 | 解析器与业务层正则**同源**，坏文件逐文件 fallback 不中断 | 数据导入器惯例（逐条容错） | ✓ 本轮修复 fallback 中断缺陷 |
| 脱敏 | 清洗→脱敏→入库顺序固定，库中无明文 PII；`--mask-all` 全链路 | GDPR/PIPL 合规工具（隐私默认） | ✓ 用户多次追问的隐私线 |
| 考核 | 规则自动扣分（可配置方案）+ AI 证据化评语**不写评分**，Rating 留给主管 | 人力资源绩效系统的人机分权惯例 | ✓ 避免 AI 直接定级风险 |
| 知识库 | 脱敏草稿 → 人工精修 → 可同步 ima/本地 | 知识管理双通道（机器草稿+人工校准） | ✓ |
| 增量 | 记忆层锚点（`state/history.json`），多群分别过滤 | 增量同步/断点续传惯例 | ✓ 二次运行实测跳过 56 条 |
| 输出 | 17 节 HTML 看板 + 快照保留 + 固定入口 `latest_report.html` | 报表工具的快照/固定链接惯例 | ✓ |
| 部署 | 零安装（豆包直接触发 / 拷贝目录 / 单脚本替换更新） | 无服务器本地工具 | ✓ 用户"别人电脑能不能跑通"关切已解决 |

### 1.3 模块职责评审（本轮复查结论）

- **数据层**：单一职责（存取/检索/报表），不掺业务统计口径；CLI 无 Web 依赖，可被任何上层调用。
- **业务层**：单脚本内按功能分区（统计/日报/跟进/考核/知识库/信号…），对外 17 个子命令；LLM 全部可降级（失败自动回退规则版，不影响主流程）。
- **辅助脚本**：`sync_kb.py`（ima 知识库同步 + COS 签名上传）、`convert_wx.py`（微信导出转标准格式）、`render_html.py`（17 节看板渲染）——各自独立、可单独测试。
- **发现并已修复的职责问题**：`kb-draft` 与 `main` 的知识库段曾各写一套 → 重构为共用 `_build_kb_section()`；`cli.py report` 与 `weekly` 参数不一致 → 合并 set_defaults 并补 `--title/--no-llm`。

## 六、已知边界与建议（务实清单）

1. **LLM 能力**：`config.json` 的 `llm.api_key` 默认为空——测试全部走 mock 不联网；接入真实 Key 后 AI 提炼（讨论要点/日报/知识库/考核评语）自动启用，失败自动降级规则版。
2. **ima 知识库同步**：`knowledge.ima` 默认未启用；配置 client_id/api_key 后可自动上传，COS 签名上传链路已 98% 测试覆盖（mock）。
3. **10 人规模定位**：SQLite 单文件足够（当前样例 56 条消息毫秒级完成）；消息量到百万级再评估迁移 DuckDB/PostgreSQL。
4. **更新体验**：Skill 形态下"更新"=替换 `.user_skills/chat-archive/scripts/chat_archive.py` 单文件，无依赖安装、无版本矩阵，符合"别人电脑可用"约束。
5. **合规**：仅处理工作群消息、不采集私聊；企业使用需员工知情同意；产物交付第三方前默认开 `--mask-all`。
